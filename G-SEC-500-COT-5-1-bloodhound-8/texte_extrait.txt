Business	impact.
	A	single	mis-provisioned	user	account	(an	SPN	bound	to	a	human	account
instead	of	a	managed	service	account,	combined	with	a	weak,	never-audited	password)	handed	an
attacker	complete	remote	code	execution	on	a	domain-joined	workstation.	Because	the	request	for	a

the	attacker	actually	logs	into

Top	recommendations.
1.	Never	bind	a	Service	Principal	Name	to	a	standard	user	account;	use	a	Group	Managed	Service
Account	(gMSA)	instead,	which	carries	a	120-character,	automatically	rotated	password	that
cannot	realistically	be	cracked.
2.	If	a	legacy	SPN-on-user-account	setup	must	be	kept	temporarily,	enforce	a	long,	random,
non-dictionary	password	on	that	account	and	monitor	it	like	a	privileged	credential.

g.clooney

local	group	memberships	granted	to	service-flavoured	accounts	across	the	domain.
4.	Detect	and	alert	on	Kerberoasting	at	the	source:	a	burst	of	RC4/AES	TGS-REQ	requests	for
different	SPNs	from	a	single	account	in	a	short	time	window	(Event	ID	4769	with	ticket

A	prerequisite	worth	documenting:	Kerberos	clock	skew
Before	any	Kerberos	exchange	could	succeed,	authentication	failed	with
KRB_AP_ERR_SKEW	(Clock	skew	too	great)
.	Kerberos	tickets	are	time-stamped	and	the	KDC	(the
Domain	Controller)	rejects	any	exchange	where	the	client's	clock	differs	from	its	own	by	more	than
5	minutes	—	a	deliberate	anti-replay	protection.	Querying	
DC01
's	own	time	service	(it	also	acts
as	NTP	server	for	the	domain,	like	most	DCs)	showed	a	
~7-hour	gap
	with	the	attacking
container's	clock.	Rather	than	altering	the	container's	real	system	clock	(which	would	also	shift
the	host's	clock,	and	which	Docker's	default	capabilities	don't	even	permit),	every	Kerberos-
dependent	command	in	this	chain	was	run	through	
faketime
,	which	transparently	fakes	the
wall-clock	time	seen	by	a	single	process	without	touching	the	real	system	time.

Kerberoasting	tool:

Cracking	tool:	
hashcat
	over	John	the	Ripper.

Decision	revised	mid-engagement:	system	clock	vs.	per-process	time	faking.
The	first	Kerberoasting	attempt	failed	with	
KRB_AP_ERR_SKEW
.	The	initial	instinct	was	to

capability)	rather	than	persisting	with	an	approach	that	would	have	required	elevated,
unavailable	permissions	or	risked	desynchronising	the	attacking	host	itself.
